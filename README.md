# ConductLens

CFPB Consumer Complaint Database + FDIC institution register + FRED daily rates
→ BigQuery sandbox **and** Databricks Free Edition (two warehouses, same raw log, same dbt project)
→ dbt (staging, intermediate, marts, snapshot, tests, docs)
→ Airflow daily (every dbt model is its own task)
→ Hex dashboard answering ten business questions for Compliance, Customer Operations and Product.

Everything runs on free tiers. Dashboard: **_link added once the first scheduled runs are in_**
(Hex Community app bound to the Databricks replica; see "Why Hex reads Databricks").

```
ingestion/   cl-ingest: download → normalise → parquet → version-log upsert into each warehouse
dbt/         conductlens project; runs on target dbx (Databricks) and bq (BigQuery sandbox)
airflow/     docker compose stack; conductlens_daily, _weekly_full_diff, _backfill DAGs (Cosmos)
hex/         the dashboard SQL per question + layout notes
scripts/     bootstrap steps for the free BigQuery / Databricks accounts, evidence helpers
docs/        ARCHITECTURE.md is the contract every component follows (tables, columns, run modes)
evidence/    scheduled-run logs and dashboard screenshots, generated by `cl-ingest evidence`
```

## Run it from clean free accounts

1. **Databricks Free Edition** (databricks.com/learn/free-edition): create a personal access token
   (Settings → Developer) and copy the SQL warehouse HTTP path (SQL Warehouses → Serverless Starter
   Warehouse → Connection details). Then `scripts/bootstrap_databricks.sh` creates the
   `conductlens_*` schemas and the `landing` volume.
2. **BigQuery sandbox**: follow `scripts/bootstrap_bigquery.md` (create a project, no billing, a
   service account with *BigQuery Data Editor* + *BigQuery Job User*, key saved to
   `secrets/bq-service-account.json`, which is git-ignored).
3. `cp .env.example .env` and fill it. `make setup` builds `.venv` and installs dbt packages.
4. `make ensure-tables` creates every raw table (and, on BigQuery, triggers the first full load).
   `make ingest-all` runs the three sources incrementally; the first CFPB run downloads the
   360 MB bulk file, converts 18.7M rows to parquet in ~25 s, and loads history quarter by quarter.
5. `make dbt-dbx` and `make dbt-bq` build the models and tests on each warehouse;
   `make dbt-docs` serves the generated docs.
6. `cp airflow/.env.example airflow/.env`, fill it, `make airflow-up`, open http://localhost:8080,
   unpause `conductlens_daily`. From here on the schedule runs unattended at 13:00 UTC.
7. **Hex**: create a Databricks connection in Hex Community with the same host/HTTP path/token,
   paste the queries from `hex/queries.sql` (one per question), publish the app publicly.

The CFPB **search API is geo-fenced** (HTTP 403 outside the US). Nothing here depends on it: the
daily bulk CSV is the primary source and is reachable everywhere. The API client exists only to
fill the API-only columns (`consumer_disputed`, `has_narrative`) when the pipeline runs from a US
network; set `CL_CFPB_SOURCE=api` to use it.

## Design decisions

**1. Complaint rows mutate, so the raw layer is an append-only version log and every run
re-pulls a trailing window.** A complaint appears in the file the day it is received; the company
response, the timeliness flag and (historically) the dispute flag fill in over the following
weeks. Loading "new rows by received date" would freeze every complaint in its day-one state. So
`cl-ingest` hashes the business columns of every complaint in the window
`[watermark − CL_CFPB_OVERLAP_DAYS (60), today]`, writes only `(complaint_id, row_hash)` pairs the
warehouse does not already have, and staging picks the newest `_loaded_at` per id. The same
procedure handles deletions: a key the warehouse has in that window but the file no longer has
gets a tombstone row. Re-running any window re-derives the same hashes and writes nothing, so
`Clear` in Airflow is always safe and a backfill of 2024 is the same code path with explicit
dates (`conductlens_backfill`, `--mode backfill`). Because the bulk file is the *whole* database
every day, a weekly `full_diff` run applies the same comparison to all 18.7M rows and catches the
rare mutation older than 60 days. On Databricks the write is `MERGE … WHEN NOT MATCHED` on
`(id, row_hash)`; on BigQuery (no DML) it is an anti-join against the window's existing keys
followed by a free load job. Both end up with the same rows.

**2. Company names are free text, so matching is a seed plus a normalised-name join, and the
match rate is published, not assumed.** The CFPB writes `JPMORGAN CHASE & CO.`; the FDIC has
several charters under holding company `JPMORGAN CHASE & CO` plus charters whose own names say
nothing about the parent. `int_company_mapping` tries, in order: the manual seed
`company_fdic_map.csv` (CFPB name → FDIC holding-company RSSD id or `CERT-<n>`), then a
normalised-name match against FDIC holding-company names, then against charter names.
Normalisation upper-cases, strips punctuation and legal suffixes (INC, LLC, N.A., CORPORATION,
HOLDINGS, FINANCIAL, BANCORP …). Every row carries `match_method`, and
`mart_company_match_coverage` reports the share of complaints per method. A singular test
**warns** when matched volume among bank-product complaints (mortgage, cards, deposits, auto,
personal, student, prepaid) drops below 85 %. Overall match rate is deliberately *not* the
headline: 80 % of all complaints are about the three credit bureaus, which are not banks and are
not supposed to match. The honest number is the bank-product one, and it is on the dashboard.

**3. Deposit normalisation only exists for chartered banks, so fintechs get their own,
unnormalised peer group.** Question 6 ranks complaints per billion dollars of deposits. PayPal,
Chime, Affirm and Coinbase have no FDIC charter and no deposits of their own (their partner
banks' deposits would be the wrong denominator). `mart_company_benchmark` therefore has
`peer_group = 'chartered'` (complaints / deposits, ranked inside deposit-size buckets <1B,
1–10B, 10–50B, 50–250B, >250B) and `peer_group = 'fintech_unnormalised'` (ranked by raw
trailing-twelve-month volume among themselves). Nobody is silently dropped; the dashboard shows
both tables side by side and says why they are different. Our bank (`CL_OUR_COMPANY`, default
`ALLY FINANCIAL INC.`, whose charter *is* in the FDIC) is highlighted in its size bucket.

**4. Narratives are never landed.** The free-text narrative is the bulk of the raw bytes
(roughly two thirds of the historic 18-column export), it contains personal detail even after
the CFPB's redaction, and not one of the ten questions needs it. The pipeline requests only
structured fields from the API (`field=` without `complaint_what_happened`) and the bulk file no
longer ships narratives at all; the schema keeps a `has_narrative` boolean so the *existence* of
a narrative can still be analysed. On the BigQuery sandbox this is also what makes the project
fit at all (see 7).

**5. Partition by received month, cluster by company.** Every dashboard query filters on a
received-date range and most group by company, so the big tables are partitioned on
`received_month_id` (an integer such as `202610`) and clustered by `company` (Databricks: liquid
clustering on `received_date, company`). Why an integer month and not a `DATE` partition: in
the sandbox every *partition* also expires 60 days after its boundary, which would delete all
history older than two months on a date-partitioned table; integer-range partitions have no
partition expiration, so they prune the trailing-window marts (Q1, Q3, Q8) without being
destroyed by it.

**6. Rates are a different grain, and the lag lives in a mart.** FRED series are daily
(DGS10, DFF, DPRIME), weekly (MORTGAGE30US) or quarterly (TERMCBCCALLNS). `int_rates_daily`
forward-fills every series onto a daily date spine; `mart_rates_weekly` averages rates and sums
mortgage and credit-card complaints by week; `mart_rates_lag_correlation` computes, for lags of
0–26 weeks, the correlation between complaint volume and the *lagged* rate, both on levels and
on 4-week changes (complaint volume grew 50× over the period, so levels alone would just show the
trend). Hex only draws the table and highlights `is_best_lag`; no lag arithmetic happens in the
dashboard, so the number is testable (`dbt_utils.accepted_range` keeps correlations in [−1, 1])
and the same on both warehouses.

**7. The BigQuery sandbox cannot hold 18.7M mutable rows, so it holds the daily-cell grain,
and Databricks is the durable system of record.** The sandbox terms (docs.cloud.google.com/
bigquery/docs/sandbox, page dated 2026-10-22) are: a **lifetime** 10 GiB of storage "not refunded
upon data deletion", **every table and partition expires after 60 days**, **no DML**, 1 TiB of
query bytes a month. Measured on the 2026-10-24 file, the complaint-level log is **7.7 GB of
BigQuery logical bytes** (5.2 GB of it the repeated product/issue/response strings). Keeping it
alive means rewriting it every 60 days: ~46 GB a year against a 10 GiB lifetime. Not possible
without billing. The ten questions, however, are all aggregates over
`(received_date, company, product, sub_product, issue, state, company_response, timely_response,
consumer_disputed)`. That grain has 5.2M cells for all of history, and with the eight string
columns replaced by integer codes (`cfpb_codes`, ~9k rows) a cell costs ~133 bytes: **0.69 GB per
60-day rotation, ~3 MB a day of new cell versions, ~3 MB a day of mart rebuilds → about 6.5 GB a
year, so the sandbox lasts roughly 18 months before billing has to be enabled** (at which point
the same data costs under $1 a month). The cell log follows the identical version-log rules
(key + `row_hash` of the count, tombstones, latest `_loaded_at` wins), and the dbt project reads
both warehouses through one model, `int_complaints_daily`: a `group by` over complaint rows on
Databricks, a decode of cell rows on BigQuery. Every mart reads only that model, so mart SQL is
byte-for-byte identical on both targets and the daily `parity_check` task compares every mart's
row count and numeric checksums across warehouses (fails above 0.1 % drift, writes
`_parity_checks`). What BigQuery gives up: zip code, tags, submission channel, sub-issue, the
date sent to company and the public response, none of which a question needs. Switching
BigQuery to complaint-level is one env var (`CL_BQ_CFPB_GRAIN=complaints`) once billing exists.

**Why Hex reads Databricks.** A Hex SQL cell is bound to one connection. If it were bound to the
sandbox, the app would go dark for the hours between a table expiring and the next scheduled
rehydration, and every rehydration would spend the lifetime budget. Databricks Free Edition has
no expiry, so the published app reads `workspace.conductlens_marts`. Because marts are identical
by construction and checked daily, rebinding Hex to BigQuery is a connection change, not a query
change.

**Other calls worth a sentence.** *Bulk file over API*: one 360 MB download gives the whole
database with a `Last-Modified` date that becomes `_source_as_of`; conditional GET (ETag) means a
rerun on the same day downloads nothing. *Dispute rate (Q5)*: the CFPB stopped collecting
"consumer disputed?" on 2017-04-24 and the bulk export dropped the column; the schema keeps it,
the API path fills it where available, and `mart_dispute_rate` publishes `coverage_share` next
to every rate so nobody reads a 2016 number as current. *15-day window (Q3)*: the CFPB's own
`Timely response?` flag is the measure; the response date is not published, so we do not
recompute it and say so in the model description. *FDIC snapshot*: `snap_fdic_institutions`
(dbt `check` strategy on name, holding company, active flag, deposits, assets) runs on
Databricks only because snapshots need MERGE; it is what makes "deposits as of the complaint's
quarter" possible later. *Codes never change*: `cfpb_codes` is append-only, so a cell written a
year ago decodes the same way today. *BNPL*: no CFPB sub-product currently contains "buy now,
pay later" (checked against all 18.7M rows), so the `bnpl` product group is wired but empty; the
Q2 panel says so and BNPL is tracked through the digital-first segment (Affirm, Klarna, Sezzle,
Zip, Afterpay inside Block) instead of pretending a product line exists. *FRED User-Agent*:
fred.stlouisfed.org drops connections for unknown User-Agent strings (curl, Wget and the
python-requests default pass; anything custom times out), so the FRED client uses the library
default and the code says why.

## Time zone

CFPB "Date received" and "Date sent to company" are US-Eastern **calendar dates** with no time
component. They are stored as `DATE`, compared as dates, and never converted. "This week", "this
month" and "year to date" in `mart_volume_periods` use today's date in `America/New_York`
(`cl_today()` macro) so a 13:00 UTC run and a 23:30 UTC run agree on what "today" is. Weeks start
on Monday. Audit timestamps (`_loaded_at`, run logs) are UTC.

## Schedule, and what a failure looks like

`conductlens_daily` runs at 13:00 UTC: the CFPB file refreshes around 09:00 UTC and FRED has
published the previous business day by then. Graph:
`ensure_tables → ingest.{cfpb,fdic,fred} → dbt_dbx ∥ dbt_bq → parity_check → write_evidence`.
The two dbt groups are independent: a sandbox quota error never blocks Databricks and vice versa.
`parity_check` and `write_evidence` run `all_done`, so the evidence row records the gap.
Sundays 14:00 UTC `conductlens_weekly_full_diff` re-hashes the entire file. `conductlens_backfill`
is manual with `start`/`end`/`sources` params.

**A red run.** Open the failed task's log. Ingest tasks end with the source, the window, and a
plain error (`HTTP 403 … blocked for this network (geo-fence?)`, `bulk download truncated: n of m
bytes`, `FDIC returned only 12 institutions; refusing to treat that as truth`). Every attempt,
successful or not, is a row in `conductlens_raw._load_runs` (`status`, `error`, rows read and
written) on each warehouse, and `_load_state` shows the watermark per source and sink; `make
evidence` renders both. Transient errors are retried twice with exponential backoff. Fix the
cause and *Clear* the task: ingestion is idempotent, so re-running never duplicates. A dbt task is
one model (Cosmos); clear just that model and its downstream. Missed days need no backfill: the
next incremental run re-pulls the trailing 60 days anyway.

**The failure this design exists for: a BigQuery table expired.** `ensure_tables` runs first on
every daily run. It reads each raw table's `expires`; a table within 5 days of expiry is rotated
(copy job → drop → rename, one write, history kept); a table that is already gone is recreated
and **rehydrated** from the day's parquet, quarter by quarter, logged as `mode = 'rehydrate'`.
Marts and views are rebuilt by dbt each day, which resets their 60-day clock. Nothing manual,
and the Hex app never noticed because it reads Databricks.

**Other failures and their recovery.** A half-finished CFPB load leaves only complete, correct
versions behind (each quarter chunk is its own upsert; the watermark moves only after the whole
window succeeds). The Databricks warehouse auto-stopping mid-run surfaces as a connector timeout
→ retry. A CFPB schema change (a renamed column) fails the parquet conversion before anything is
written. An empty FDIC answer is refused rather than loaded, so `dim_company` can never lose its
deposits silently.

## Evidence of unattended runs

`evidence/scheduled_runs.md` is written by the last task of every daily run from `_load_runs`
and `_parity_checks`; `evidence/airflow_runs_<date>.md` is `airflow dags list-runs`; dashboard
screenshots are added by hand. The first end-to-end run (2026-10-24, run
`scheduled__2026-10-23T13:00:00+00:00`, 99 tasks, 21 min) is in the file; it also records two
real failures and their recoveries: the ingest tasks failing on a CLI argument bug (fixed, group
cleared, re-ran idempotently with 0 rows written) and `mart_rates_lag_correlation` failing on
BigQuery because `groups` is a reserved word there (fixed, single model cleared, 4 tasks re-ran).
_The two unattended 13:00 UTC runs the brief asks for will be appended as they happen._
